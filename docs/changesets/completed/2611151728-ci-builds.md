# CI Builds for Windows and macOS

- Status: Implemented
- Id: 2611151728-ci-builds
- Depends-on: 2611151521-telaelus-rename

## Summary

A GitHub Actions workflow tests the game and exports playable Windows and macOS builds as
downloadable artifacts. The workflow only calls one export script, and the same script runs on
this machine, so a build can be proven locally before anything is pushed. The workflow itself can
also be run locally in Docker with `act`.

## Motivation

There is no way yet to hand someone a build: the game runs only from the editor. Exports also
need things nothing checks today: export presets, export templates matching the editor version,
and a C# publish per platform. A build that breaks should fail on the commit that broke it, not
on the day someone wants to share the game. The repository has no GitHub remote yet, so the setup
must be testable here first.

## Design

### One export script, run the same everywhere

- `ci/export.py` (Python 3, standard library only) does the whole build:
  1. Reads the Godot version from one place (`ci/godot-version.txt`, `4.7.2-stable`), downloads
     the matching Godot .NET editor for the host and the .NET export templates from the official
     GitHub releases into a cache folder (`.ci-cache/`, git-ignored), self-contained, and extracts
     only the templates the presets need beside it. Locally it runs the same way; `--editor`
     uses an installed editor instead.
  2. Imports the project headless (`--headless --import`).
  3. Exports each preset with `--headless --export-release "<preset>" <path>`.
  4. Zips each build into `dist/` (git-ignored) with the version and commit in the name:
     `Telaelus-<version>-<commit>-windows-x64.zip`, `...-windows-arm64.zip`, `...-macos.zip`.
- `ci/export.py --platform windows|macos|all` picks what to export; `--editor <path>` overrides
  the editor.

### Export presets

- `src/Telaelus/export_presets.cfg`, committed:
  - **Windows Desktop x64** and **Windows Desktop arm64**, each one `.exe` with the `.pck`
    embedded, plus the .NET data folder.
  - **macOS**, universal (x86_64 and arm64), exported as a `.zip` holding `Telaelus.app`.
    Exporting as a `.zip` keeps the executable flag on files built from Windows or Linux.
- Debug-only code (the scenario runner and control channel) already stays out of release builds;
  release exports use `--export-release`.

### Signing (first pass)

- **Windows:** unsigned. SmartScreen warns on first launch ("More info" then "Run anyway").
- **macOS:** ad-hoc signed (Godot's built-in signer), not notarized. Gatekeeper blocks a
  downloaded app the first time; the player opens it with right-click then Open, or System
  Settings > Privacy & Security > Open Anyway.
- Proper signing (an Apple Developer ID with notarization through `rcodesign`, a Windows code
  signing certificate) is a later changeset; it needs paid certificates and repository secrets.

### The workflow

- `.github/workflows/build.yml` uses GitHub's standard actions for what is about the runner, and
  the script for what is about Godot:
  - standard steps: `actions/checkout`, `actions/setup-dotnet` (the SDK the solution needs),
    `actions/setup-python`, `actions/cache` (the Godot downloads in `.ci-cache/`, keyed on
    `ci/godot-version.txt`), and `actions/upload-artifact`;
  - script steps: `python ci/export.py --setup` (download and install Godot and the templates),
    then the tests or the export.
  - No third-party Godot actions: what they do is the part we want to run locally without
    GitHub, and they would be outside code in the build.
- **test** (`ubuntu-latest`), on every push and pull request: `dotnet test
  src/Telaelus.Sim.Tests`, then `dotnet test src/Telaelus.Integration.Tests` with the Linux Godot
  .NET editor from the setup step.
- **export** (`ubuntu-latest`, after test), on pushes to `main`, on tags, and by hand
  (`workflow_dispatch`): `python ci/export.py --platform all`, then uploads each zip in `dist/`
  as a workflow artifact (kept 14 days). Attaching builds to GitHub Releases is later.
- Both platforms export from one Linux job: Godot exports Windows and macOS from any desktop
  host, and a Linux job is the one kind `act` can run in Docker. A macOS runner is only needed
  later, for iOS or Apple's own signing tools.
- The downloads are cached between runs (`actions/cache` keyed on the Godot version).

### Testing it locally, before GitHub

Three levels, cheapest first:

1. **The script on this machine:** `python ci/export.py --platform all` exports both builds with
   the editor from `tools.json`. Unzip and run the Windows build here.
2. **The workflow in Docker with `act`:** install `act` (`winget install nektos.act`) and start
   Docker Desktop, then `act push -j export` (or `-j test`) runs the Linux jobs in a container
   that mirrors GitHub's Ubuntu runner, downloads and all, and `--artifact-server-path` keeps
   the zips. This machine is ARM64, so the containers run as `linux/amd64` under emulation
   (slow, but the same image GitHub uses), or as `linux/arm64` with the arm64 Linux editor.
3. **A first push to a private GitHub repository** once 1 and 2 pass.

The macOS build cannot be launched on this machine; level 1 checks that it exports and that the
`.app` inside has the expected layout and its .NET assemblies. Running it needs a Mac.

## Verification

- `python ci/export.py --platform all` here produces both zips; the Windows build launches from
  the unzipped folder, reaches the main menu, and starts a new game.
- The macOS zip holds `Telaelus.app` with `Contents/MacOS/Telaelus` and the .NET data.

## Decisions

1. **Apple scope:** macOS only; iOS later.
2. **Signing:** unsigned Windows and ad-hoc macOS for now; real signing is its own changeset.
3. **Architectures:** Windows x64 and arm64, and macOS universal.
4. **When it runs:** tests on every push and pull request; exports on `main`, tags, and by hand.
5. **Releases:** later.
6. **Workflow shape:** standard GitHub actions for checkout, the SDKs, caching, and artifacts; the
   script for everything Godot; no third-party Godot actions.

## Implementation notes

- **Godot found no solution:** it looks for `Telaelus.sln` beside the project, and without one an
  export skips the C# build and still exits 0, leaving a build with no game code.
  `dotnet/project/solution_directory="../.."` points it at `Telaelus.slnx` at the repo root, which
  Godot 4.7 accepts. The script fails any build without `Telaelus.dll`.
- **macOS needed S3TC/BPTC textures** for its x86_64 half
  (`rendering/textures/vram_compression/import_s3tc_bptc=true`); one texture's `.import` gains
  the desktop format.
- **The script's commands** are `setup`, `import`, and `export`. Only the three templates used are
  kept from the 1.1 GB archive (about 580 MB cached with the editor). Godot's output is read from
  `--log-file`, since the Windows editor prints nothing when redirected.
- **`.actrc`** gives `act` the runner image and `DOTNET_SYSTEM_GLOBALIZATION_INVARIANT=1`: the
  `catthehacker/ubuntu:act-latest` image has no ICU library, which GitHub's runner has.
- **Verified:** all three builds export here; the Windows arm64 release build reaches the main menu
  and starts a new game; `act push -j test` passes (352 sim and 69 integration tests on Linux
  arm64) and `act push -j export` exports all three and uploads them, restoring the Godot cache
  saved by the test run. The macOS build was checked for layout, both architectures' assemblies,
  and its executable flag, not launched. The first GitHub run is the first on x64 Linux.
- The macOS bundle identifier `com.telaelus.game` is a placeholder until signing.
